# Proof of value: change one decision, regenerate, see exactly what moved

Reproduce (repo root, stdlib only):

```text
python -m tooling.python.demo_decision_change                         # password-reset
python -m tooling.python.demo_decision_change --app expense-approval
python -m tooling.python.demo_decision_change --app shared-tasks
python -m unittest tooling.python.test_demo_decision_change
```

## What the demo does

1. Resolves one consequential decision with option A through the public agent
   (`OrinDecisionAgent.apply_decision`), generates code with
   `python -m implementations.python.codegen.generate`, replays the shared
   acceptance cases.
2. Changes **only the decision** to option B, regenerates, replays again.
3. Reports the generated-code diff, which cases change outcome, and (for
   password-reset) what stayed byte-identical.

## Three apps, one decision each

| App / decision | Generator | Generated-code diff | Shared conformance cases | Demo-only probes | Verdict |
|---|---|---|---|---|---|
| password-reset: `rate-limit` (5/15min/origin vs 3/h) | Hand-written template, constants parsed from claims | 3 lines out, 3 in (`RATE_LIMIT_*`); 18 of 19 blocks identical | 8/8 pass under both; none change (no rate-limit cases exist) | 3 of 6 outcomes flip | Decision change realised, but only as constants |
| expense-approval: `no-eligible-approver` (escalate / reject / stay-submitted) | Hand-written template; TypeScript generator accepts only `stay-submitted` | **0 lines** between any options | 10/10 pass under all (they encode stay-submitted) | Escalate and reject are **not** implemented: code still leaves the expense submitted | Decision recorded in the model, **not** reflected in generated code |
| shared-tasks.minimal: `non-member-assignee-completion` (membership-required vs assignee-may-complete) | Model-driven (`codegen/model_driven.py`) | ~13 lines of IR/report text; adds one `NotImplementedRule` hook | membership-required 4/4; assignee-may-complete 3/4 (hook raises on member-completes) | Non-member assignee still unauthorized under both | New rule surfaces as a loud hook, not silently ignored; behaviour needs human code |

The expense row is a negative result: the diff is empty because the Python
template ignores the chosen option. The stay-submitted column uses the shipped
`expense-approval.resolved.model.json`, since the agent's prompt offers only
escalate and reject.

## Password-reset detail

- **Generated-code diff:** 3 lines removed, 3 added, all `RATE_LIMIT_*`
  constants (`5/900/True` -> `3/3600/False`).
- **Unchanged rules:** 18 of 19 top-level generated blocks are byte-identical
  (token expiry, single use, no-disclosure, capabilities, response shape); the
  19th is the constants header.
- **Demo-only probes that change (3 of 6):** 4th request in 10 minutes from the
  same origin, from different origins, and 20 minutes after three (all
  sent -> not-sent). Unchanged: first request, 6th in 10 minutes, request after
  one hour. These probes are supplied by the demo, not by `tests/conformance/`.
- **Meaning:** A = 5 per 15 min per address *per origin*; B = 3 per hour per
  address regardless of origin; over the limit the person still sees the
  standard confirmation and no message is sent.

## Honest comparison with hand-written code (password-reset)

Hand-written runtimes (`python/password_reset.py` 163 lines,
`typescript/src/password_reset.ts` 107) contain no rate limiting; only the
proof harnesses exercise it. The fair comparison is a human adding the rule:

| | Orin | Hand-written |
|---|---|---|
| Source edited | 1 decision choice | Rule logic per runtime, plus origin plumbing |
| Lines changed by hand | 0 (regenerated) | Estimated 10-15 per runtime |
| Review surface | 6-line diff | Whole-function diff |
| Re-test | Same cases replayed | Author updates examples |

Hand-written figures are estimates, not measurements. For expense-approval and
shared-tasks the honest count is: Orin edit = 1 option choice, but a human
still hand-writes the escalate/reject behaviour (expense) and the assignee
hook (shared-tasks); only password-reset is fully automatic.

## Not proven yet

- No controlled hand-coding comparison: nobody was timed; effort is estimated.
- Probes are demo-only (labelled in the output), not shared conformance
  cases: rate-limit outcomes, expense escalate/reject outcomes, and the
  non-member-assignee probe. Promote them to `tests/conformance/` to count.
- Only 1 of 3 apps (password-reset) turns the decision into changed behaviour
  automatically, and only by filling constants from claim text by regex.
- Expense-approval escalate/reject are not generated by Python; TypeScript
  refuses anything but stay-submitted.
- Shared-tasks assignee-may-complete yields a `NotImplementedRule` hook, so
  even the shared member-completes case fails until a human implements it.
- Whether option text matches stakeholder intent is a human judgement.
- In-memory, single-process runtimes; no persistence, concurrency or clock
  skew. Decisions that restructure behaviour are not shown to be cheap.
- Python/TypeScript parity of decision-change behaviour is not demonstrated.
